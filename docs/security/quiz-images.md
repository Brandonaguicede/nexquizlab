# Private quiz image lifecycle

All authoring and image endpoints require the existing offline RS256 verifier. Subjects own resources; ownerId input is forbidden. Missing, foreign and deleted resources return the same 404. Images are retrieved with Bearer auth and private,no-store headers. JWTs never enter image URLs or browser storage. Web fetches Blob URLs in memory and revokes them on unmount; the proxy CSP permits blob images. API paths are relative to the API origin, so another device can use the same API with its own valid session.

Uploads use disk-backed multipart buffering, one file, no extra fields, 5 MiB maximum. The server decodes real JPEG/PNG/WebP content with Sharp, rejects unsupported/animated files and dimensions over 16 million pixels, fully re-encodes WebP and strips metadata. Original names, extensions and MIME values never form storage paths. Object IDs are UUIDs validated again by the storage adapter. JPEG/PNG/WebP input becomes WebP output intentionally. Sharp file caching is disabled so temporary uploads can be unlinked on Windows.

The asset row is allocated before the filesystem write. The normalized file is atomically renamed on the same volume, then associated under the parent transaction lock. A failed attach removes the new file; if that cleanup fails the durable unreferenced row remains. Stale uploads cannot attach after 30 minutes; the collector reclaims unreferenced pending rows older than one hour. Replacement/removal marks old assets detached inside the transaction. Every minute and at startup the collector removes up to 100 eligible objects and then their rows. Failed deletions keep their rows for retry and log only a generic warning. Temporary files older than one hour are collected, including interrupted uploads. Active assets are never eligible for collection. This intentionally provides eventual cleanup rather than pretending the DB and filesystem share a transaction.

Local adapter uses IMAGE_STORAGE_PATH, default /app/images in Docker; named volume nexquiz-images persists restarts. The application depends on ImageStorage, not filesystem paths. A future object-store adapter can implement the same save/open/remove lifecycle; multipart temporary buffering remains a transport concern. Upload concurrency currently follows the single Game instance; deployment should enforce disk quotas and request throttling if exposed publicly. No cache or external publication was introduced.

## Other-device verification

Default development Compose binds 127.0.0.1 to preserve existing exposure. For a controlled LAN demo create a local Compose override that replaces only the web port binding with HOST_LAN_IP:8080:8080 and add http://HOST_LAN_IP:8080 to CORS_ORIGINS in the local environment before recreating Auth/Game/Web. Do not expose PostgreSQL or Grafana. Use the same host URL for Web and the relative /game and /auth proxies, never localhost on the remote device. Production should use the existing HTTPS Caddy host, secure Auth cookies and persistent volume. Physical second-device validation requires a reachable host and is reported separately from automated alternate-host browser testing.
