# Authoring aggregates and future immutable game snapshots

Game owns Quiz, Question and ImageAsset. ownerId is a JWT subject, with no foreign key, join or credentials from the Auth database. Domain rules are framework independent; application ports isolate Prisma and local storage. Presentation owns DTO validation and Bearer guards; composition occurs only in modules.

Quiz title is trimmed (1–160), description optional (0–2000); question prompt is trimmed (1–2000), correctAnswer a real boolean. Active questions have contiguous zero-based positions; maximum 200 per quiz bounds editor payloads and mutation duration. List pagination is 1-based, default 10, max 50, with a page safety ceiling of 1,000,000. List and count run in one repeatable-read transaction. The query uses a filtered relation count, never a query per quiz. The (ownerId,deletedAt,updatedAt DESC,id) index follows ownership, active filtering and deterministic ordering.

Every aggregate mutation locks the owned Quiz row in PostgreSQL. Reorder validates a complete permutation, temporarily releases unique positions using NULL and assigns all positions in one set-based UPDATE within the same transaction. Readers never observe the intermediate state. The unique (quizId,position) index prevents collisions; deleted rows use NULL positions. A stale permutation returns 409. Concurrent append, removal, metadata edits and image association serialize on the same row. No process-only lock or cache is used.

Deletes are tombstones; SQL foreign keys use RESTRICT, never CASCADE. Deleting a quiz tombstones its active questions and detaches images transactionally; repeating the owned deletion is harmless. This preserves source identifiers and authoring text for future references, while management queries and reads exclude deleted records. It is not a complete game-history implementation.

## Snapshot contract for Hito 4

When a future game begins, its transaction must lock the Quiz, confirm the game initiator owns it, select the complete active ordered questions, validate playability and copy values into immutable GameQuestionSnapshot rows. Proposed fields: id, gameId (RESTRICT), sourceQuestionId (nullable provenance only, RESTRICT), sourceQuizId, schemaVersion=1, prompt, correctAnswer, position and snapshotImageId. A unique (gameId,position) constraint freezes order. Store quiz title/description in GameSnapshot as values, not live joins. Scoring and answers reference snapshot IDs exclusively.

Snapshot image objects must be independent retained copies or use a separate durable immutable-asset reference table. The current ImageAsset.question relationship and collector are exclusively for authoring; do not point snapshots at those assets without first adding snapshot retention and updating the collector. In the future, copy/retain image objects before committing the snapshot with a durable staging record and compensating cleanup. Later source edits/deletion must not alter historical questions, answers or images. Tests for that future change must include concurrent start/edit/delete and retained image reads. No rooms, games, roles, scores or live engines are introduced in Hito 3.
