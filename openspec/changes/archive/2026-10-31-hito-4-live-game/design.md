## Context
Game keeps four layers. Game rules (state transitions, answer window, scoring, ranking, join codes) live in `domain/game.ts` as pure functions with unit tests. Use cases live in `application/` (`CreateSession`, `JoinSession`, `StartSession`, `CloseQuestion`, `NextQuestion`, `SubmitAnswer`, `FinishSession`, `GetSessionState`, `GetResults`) and depend on ports `GameRepository`, `ImageStorage`, `LiveNotifier` and `Clock`. Prisma, file copy, timers and Socket.IO are infrastructure adapters; REST controllers and the Socket.IO gateway are Presentation and only call use cases. The existing architecture check MUST keep passing.

## Decisions
- **Commands over REST, push over WebSocket.** Every state change (create, join, start, close, next, answer, finish, cancel) is a documented REST endpoint with OpenAPI, the same guard and the same validation. The gateway only subscribes clients to rooms, pushes events and syncs state. Benefits: one authorization path, Scalar-testable contract, external consumers can drive or read a game without sockets. Cost: one extra HTTP round trip per answer (acceptable for classroom latency).
- **Snapshot at session creation.** Creating a session locks the owned Quiz, rejects quizzes without questions, copies ordered questions into GameQuestion and copies each image file into a GameImage with its own UUID (new `ImageStorage.copy(sourceId, targetId)`). Authoring edits/deletes and the authoring image collector never touch the snapshot. Answers and scores reference GameQuestion ids only.
- **Join codes.** Six characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0/O/1/I), `crypto.randomInt`, unique among non-terminal sessions via a partial unique index; retry on collision.
- **Participants.** Unique (sessionId, userId). New joins only in LOBBY; existing participants may rejoin in any non-terminal state (reconnection). Display name comes from the JWT `name` claim (fallback "Participante"). The host is not a participant. Limit `GAME_MAX_PARTICIPANTS` (default 50, env-configurable, stored per session); exceeding it returns 409 `ROOM_FULL`.
- **Server clock.** On open: `openedAt = now`, `deadline = now + questionSeconds` (default 20, allowed 5–120, chosen at creation). An answer is accepted only if status is QUESTION_OPEN, the question is current and `receivedAt <= deadline`; otherwise 409 `ANSWER_WINDOW_CLOSED`. No grace period. An in-process timer closes the question at the deadline; every read/command also closes lazily if `now > deadline`, and on boot open questions past their deadline are closed and future ones rescheduled. Clients render the countdown from `deadline` and `serverNow` (offset-corrected), never from a local start.
- **Idempotent answers.** `Answer` has UNIQUE (gameQuestionId, participantId). Insert uses `ON CONFLICT DO NOTHING`; a resubmission returns 200 with the original stored answer and `duplicate: true` and never changes score. Correctness is computed server-side from the snapshot at insert time.
- **Reveal and scoring.** `correctAnswer` is never sent while a question is open. On close, Game broadcasts the correct answer and counts (true/false/no answer); each participant receives their own result. Score = number of correct answers (1 point each, 0 for wrong or missing). Ranking: score desc; ties share rank and are listed by display name. On finish, GameResult rows (participantId, score, correctCount, rank) are written in the same transaction that sets FINISHED.
- **Host controls.** Only `hostId == JWT sub` may start, close early, advance, finish or cancel; others receive 403. `next` is only valid in QUESTION_CLOSED; after the last question `next` finishes the session.
- **Images during play.** `GET /sessions/:id/questions/:gameQuestionId/image` is allowed to the host, and to participants once that question has been opened (position <= current). Fetched as an authenticated Blob, like authoring.
- **Realtime transport.** Socket.IO namespace `/live`, path `/socket.io` (proxied as `/game/socket.io`). Handshake `auth: { token }` verified with the existing `IdentityVerifier`. Because access tokens last 300 s, clients send `auth:renew { token }` before expiry; the server disconnects with `auth:expired` when the current token's `exp` passes. Rooms: `session:{id}` (everyone), `session:{id}:host`, `session:{id}:user:{sub}` (per-user results, scoped to the session so nothing leaks across rooms). A separate `LiveBroadcaster` implements `LiveNotifier` so use cases never depend on the gateway. Clients join with `session:subscribe { sessionId }`; the server verifies host or participant and replies with `session:state`. Room isolation is enforced by subscription checks, never by client-chosen room names.
- **Events (server → client)**, all with `sessionId` and monotonically increasing `version`: `session:state` (full snapshot: status, current question without answer, deadline, serverNow, participant count, own answer and score; host also gets participant list), `participant:joined` (registration, host room), `participant:online` / `participant:offline` (socket presence only, host room), `question:opened`, `question:closed { correctAnswer, counts }`, `answer:result { correct, score }` (user room), `answer:count` (host room), `session:finished { ranking }`, `session:cancelled`, `error { code, message }`. Clients discard events with a version lower than their current one and resync with `session:subscribe` on any gap.
- **Reconnection.** Socket.IO reconnects automatically; on `connect` the Web client gets a fresh access token (refresh), re-subscribes and renders `session:state`. Because the participant and answer rows are unique, reconnecting never duplicates participation or score. Presence (`connected`) is in-memory and only informational.
- **Concurrency.** Session commands lock the GameSession row (`SELECT … FOR UPDATE`); timer close and host close race safely because the transition is checked inside the lock.

## Data model (nexquiz_game)
GameSession(id, code, hostId, sourceQuizId, title, status, questionSeconds, maxParticipants, currentPosition?, openedAt?, deadline?, version, createdAt, startedAt?, finishedAt?) · GameQuestion(id, sessionId, position, prompt, correctAnswer, imageId?) UNIQUE(sessionId, position) · GameImage(id, sessionId, createdAt) · Participant(id, sessionId, userId, displayName, joinedAt) UNIQUE(sessionId, userId) · Answer(id, gameQuestionId, participantId, value, correct, receivedAt) UNIQUE(gameQuestionId, participantId) · GameResult(sessionId, participantId, score, correctCount, rank) PK(sessionId, participantId). Foreign keys RESTRICT; partial UNIQUE(code) WHERE status NOT IN ('FINISHED','CANCELLED').

## Risks / Trade-offs
In-process timers and Socket.IO rooms bind live play to one Game instance; restart recovery is covered, scale-out is not. Strict deadlines may reject answers from very slow networks; the cut-off is visible in the UI. Copying images per session uses disk proportional to sessions; finished-session image retention is kept (results are historical) and documented. A participant can rename themselves only through Auth profile.
